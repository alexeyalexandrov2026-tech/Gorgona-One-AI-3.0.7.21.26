## Acceptance

- Three roles: customer, partner, administrator/owner. The owner is the administrator, not a fourth role.
- A partner can save and resume a structured car, yacht or accommodation draft, upload/reorder/remove photographs, preview its standard card, submit for review, see the decision/reason, revise and resubmit, and withdraw their own publication.
- The administrator sees submitted content, photographs, private contacts, version and any live publication; approval publishes exactly the reviewed version. Rejection requires a reason. Concurrent edits and repeated requests cannot publish an unreviewed version or duplicate a listing.
- Only the last approved snapshot appears publicly. Editing, submitting or rejecting a replacement preserves the previously approved snapshot. Withdrawal removes it. Stable UUID-based slugs cannot overwrite existing editorial inventory.
- Public catalogues and detail pages reuse the existing inventory repository, ListingCard, Gallery, Specs and BookingForm. Existing editorial records and the YATR/Stay22 supplier widgets remain unchanged. There is no partner-controlled HTML, CSS, card template or featured placement.
- Private draft photographs are served publicly only while referenced by the current approved snapshot. Uploads are authenticated, bounded and restricted to validated raster images. Contact details stay private by default; public requests use Miami Elio's existing booking form.
- A successful submission/decision queues the existing durable owner notification event. Draft typing does not send events. Actual external delivery remains gated by the existing channel configuration and separately authorized activation.

## Reuse and boundaries

`public.partner_listings` already owns partner submissions and existing RLS/legacy moderation. Extend it with a versioned candidate document and review state, retaining legacy columns for backward compatibility. Server-only commands authenticate through the existing dashboard identity verifier and enforce actor role, ownership, version and idempotency inside the database as well. Browser writes cannot modify versioned candidates or publish snapshots directly. Legacy rows remain private until a partner completes the structured form.

The checked-in generic `public.listings` reader is already the inventory abstraction, but its table definition is absent from this checkout and the world pages currently bypass it. Do not assume or rewrite that unverified table. Add an approval-owned `public.partner_publications` snapshot source to the existing repository and route the three affected world/detail pages through it. The snapshot contains public fields only; candidate contacts and the audit history are excluded. Static editorial seeds remain available when the database is unavailable.

Trust trace: untrusted partner form/file -> deterministic category/size/type validation -> verified Auth identity and protected profile -> service-only versioned database command -> administrator approval -> public snapshot -> escaped existing card/detail components. Media storage keys are generated by the server and scoped to the authenticated owner. Public media reads derive a storage key from the approved snapshot, never a caller-provided remote URL. Credentials remain server-side. External notification destinations remain owner-configured, never partner-controlled.

Use a private `partner_listing_images` bucket for new images; do not silently privatize the legacy public bucket or remove existing media. Storage provisioning and deployment are reviewed separately. No production keys, account elevation or cloud writes are needed for local acceptance.

## Verification and release gates

Focused contract, SQL, API, media and inventory tests cover ownership/role forgery, invalid fields, malicious image paths/types, stale decisions, replay conflicts, pending/rejected invisibility, preservation of the live revision, withdrawal, category separation and duplicate prevention. The SQL-backed browser fixture exercises all three listing categories and the moderation/publication journey; these are local fixtures, not real cloud acceptance.

An independent security/data reviewer examined the final change and reported no remaining actionable blockers. Real Supabase Auth/RLS/Storage, encrypted runtime secrets, owner-channel receipt and authenticated hosted browser acceptance remain separate release gates. Publishing the branch can trigger the currently unsafe production-targeting non-main Cloudflare deployment; keep this branch local.

Rollback: withdraw the partner snapshot through an audited command; retain candidate/audit data. Roll back application code only while preserving the schema and private media. Do not drop partner records, rewrite existing editorial inventory or run a destructive down migration as rollback.

## Hosted activation sequence

1. Resolve the production-targeting wildcard Cloudflare trigger before any branch push. Run exact-commit CI on the isolated feature branch; do not merge to main as a shortcut.
2. Inspect/backup the protected staging database and verify all earlier dashboard migrations there. Apply `supabase/migrations/20261023200000_partner_publication.sql` only to the confirmed staging project, then the separate `supabase/storage/partner-listing-images.sql`. The latter refuses a pre-existing public/unlimited bucket and adds a restrictive browser policy; existing `listings_media` stays unchanged.
3. Build the saved commit through `scripts/dashboard/workers-build.mjs` using the real staging public configuration, then use the protected staging configuration and existing secret-management flow. The fixture build above has no staging release receipt and must not be promoted as one.
4. Verify staging role provisioning, actual JPEG/PNG/WebP upload, blocked direct bucket reads, all three categories, unavailable-photo approval refusal, concurrent review, publication/withdrawal and no public contacts. Confirm owner notifications against separately authorized test destinations before enabling delivery.
5. Only after that acceptance and separate production approval, prepare the production migration/storage/runtime rollout. The current production site does not contain this feature.

The new private bucket retains registered photos, including photos referenced only by past audit revisions or removed from a candidate. No automatic destructive cleanup is enabled. The initial limits are 20 selected images per listing, 8 MB per image and 100 registered uploads per owner per day. Agree retention/cleanup and monitor storage before broad partner onboarding. A failed upload-registration attempts object deletion; if Storage itself refuses cleanup, the server emits a generic reconciliation error without exposing a key or private path.

Public enquiries use the existing Miami Elio booking form and durable request workflow. Structured contact fields are excluded from public snapshots; partner-authored description text still requires the administrator's review. Saved client-side autocomplete and homepage highlights continue to use editorial seed data; newly approved partners appear in the three category catalogues/detail pages and are not automatically promoted to homepage highlights.

Entry points after activation: `/login` -> `/profile`; protected `partner`/`admin` profiles can open `/partner`, only a protected `admin` profile can open `/admin`. User metadata and URL guessing cannot grant administrator access. The owner's actual hosted administrator role has not been verified.
