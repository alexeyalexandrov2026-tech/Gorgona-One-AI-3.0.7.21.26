The private-staging-only audit covers 94 localized initial requests, two multi-turn follow-ups and 16 unrelated questions: **112 scenarios per engine**, across all 16 supported languages. Topics include restaurants/VIP nightlife, yachts, cars, villas, flights/hotels, private jets, experiences, events and sportsbook. Mixed requests retain both destinations; a new explicit topic takes priority; unrelated arithmetic clears stale product recommendations.

Each request uses the actual form and request serialization. Chat requests are intercepted and aborted before the server; other same-origin non-GET/HEAD requests are blocked and fail acceptance. The actual UI must show its localized unavailable response and usable canonical recommendation. Navigation waits for the visitor's click. Destination links are followed and checked with authenticated GETs returning HTTP 200. The next request returns through the floating concierge and its Discovery Room link, exercising the actual visitor path. Unique request IDs and absence of unexpected writes are checked. These are offline-recovery tests, not live AI response or reservation-creation tests.

## Retained failures and limits

The initial en/ru pilot passed 26/28 and failed when its locale init script touched storage inside a sandboxed supplier iframe. The harness now seeds only the top-level page; supplier permissions were not changed. A subsequent WebKit run passed 30/112 because it read saved history before React's passive storage write completed. It now waits for this exact user/assistant turn, rather than only for the input to become enabled. These were harness corrections, not product fixes. Artifacts remain in `concierge-journey-pilot/` and `concierge-journeys-webkit/`.

A separate forced-document-reload run passed **105/112 in WebKit, exit 1**, with seven same-origin access-control messages from departing event-page fetches/prefetches (`concierge-journeys-final-webkit/results.json`). Chromium passed 112/112 in that mode (`concierge-journeys-final-chromium/results.json`, exit 0). The WebKit symptoms are consistent with [the upstream document-replacement cancellation report](https://github.com/microsoft/playwright/issues/43120), but the exact engine cause was not independently proven here. This limitation is **not fixed or declared passing**. No page-error filter was added. Explicit `CONCIERGE_JOURNEY_RETURN=reload` retains that mode; default `dock` tests normal UI return. Passing the visitor path does not erase the failed reload diagnostic.

Remaining outside these checks: live model correctness, partner availability/booking/confirmation, actual microphone input, real Safari/iOS, the earlier intermittent hydration cause, and public launch policy/abuse controls.
